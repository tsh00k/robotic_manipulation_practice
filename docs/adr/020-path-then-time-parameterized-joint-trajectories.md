# ADR 020: 先定路径、再定时间的关节轨迹

- 状态：已决定
- 日期：2026-10-07
- 范围：`task_executor` 每个阶段发给 bridge 的运动指令；`mujoco_bridge` 对关节指令的执行
- 关联：[Week 5 “Stage 3 之前：executor 运动的技术路线”](../../Job_guides/my_study/week5.md#stage-3-之前executor-运动的技术路线已定adr-020)；[Week 5 第 2 节](../../Job_guides/my_study/week5.md#2-关于运动的讨论为什么要轨迹插值)；[ADR 001](001-cartesian-task-waypoints.md)

## 背景

每个阶段 executor 用离线 IK 求一个终点关节构型，作为阶跃目标发给 bridge；bridge 只取 `JointTrajectory.points[0]` 写进位置伺服的目标。伺服以力矩上限冲向目标，实测 joint4 峰值 4.54 rad/s、99 rad/s²，TCP 2.3 m/s、37 m/s²，超过真实 Panda 的限值（关节速度 2.175 / 2.61 rad/s，libfranka 会中止超限的运动）；搬运期的打滑与高加速度段同时出现（Week 5 Stage 1）。数据契约 v0.2 也要求 action 平滑。

## 决策

1. **路径与时间分开处理。** 每个阶段：先由 IK 定出几何路径，再对整条路径做时间参数化，得到 $q(t)$。
2. **路径：关节空间直线，竖直的接近与离开用 TCP 直线。** 一般两端各一次 IK，中间 $q(s) = q_a + s\,(q_b - q_a)$。抓取下降、抬起、放入下降、退出（GRASP、LIFT、PLACE、RETRACT）走 TCP 直线：每 5 mm 一个位姿逐点 IK，以上一点为初值，相邻点关节差 > 0.05 rad 判失败（`TRAJECTORY_FAILED`）。原定全部用关节空间直线，Week 5 Stage 3 实测抓取下降、抬起时实际 TCP 离竖直线 5.7~9.2 mm，超过写定的 5 mm，按本条原有的约定改为 TCP 直线（之后 0.7~1.5 mm）。
3. **时间参数化用 TOTG**（`moveit_core` 的底层类 `trajectory_processing::Path`、`Trajectory`，直接输入关节向量，不需要 MoveIt 的机器人模型）。速度上限取 FCI 的 FER 值的 95%（2.066 / 2.480 rad/s；Week 5 Stage 6 加的余量：用 100% 时匀速段相邻 0.1 s 帧的变化恰好等于数据契约的门槛，导出器的严格比较会因舍入误差随机拒绝）；**加速度上限取 FCI 值的 1/4**（3.75、1.875、2.5、3.125、3.75、5、5 rad/s²），与 MoveIt 官方 Panda 配置相同。每个阶段一条轨迹，起止静止。
4. **加加速度不单独限。** TOTG 的加速度分段常数；取 1/4 的加速度后，加速度在 1 ms 内从 $-\ddot{q}_{\max}$ 跳到 $+\ddot{q}_{\max}$ 也不超过 FCI 的加加速度上限（例如 joint1：$2 \times 3.75 / 0.001 = 7500$），所以不需要 Ruckig。
5. **执行：** executor 在进入阶段时发出一条带时间的多点 `JointTrajectory`，每 1 ms 一个点（真机的控制周期）；bridge 记下到达时的仿真时间，每个物理步按经过的时间在点之间线性插值，写入伺服目标（同时是 pi0.5 远程推理端需要的“按时间执行动作块”的接口）。每段从上一段参考的终点出发，reset 后的第一段从 reset 的姿态出发（不用实测关节：它在重力下有几毫弧度的静差，用它当起点等于一个小阶跃）。阶段在轨迹走完之前不结束。

## 理由

- 只有对整条路径做规划才能“提前刹车”：每一步只看当前误差的做法（下面第一条被否决的做法）要么起步速度跳变、要么拖长尾或冲过头。
- 限值加在关节空间，直接对应 libfranka 检查的量；伺服对光滑参考只会延迟约 0.1 s、不会更快（Week 5 B 的单关节模型），参考满足限值，实际运动也满足（前提是力矩不饱和，Stage 3 实测）。
- TOTG 成熟、已安装，路径固定后能精确求出时间最优解。对现在的两点直线它等价于闭式梯形（用不到它处理曲线路径的能力），仍选它是为了以后加 TCP 直线、多点路径时不用换实现。

## 局限

- 关节空间直线段 TCP 走曲线（搬运段离直线几十毫米），只对竖直段做了 TCP 直线。
- 点间线性插值要求采样足够密：三次 Hermite 插值 10 ms 采样在 TOTG 的加减速切换处使加速度超限 24%，2 ms 采样在 1 ms 上看加速度是上限的 2 倍（Week 5 Stage 3）；1 ms 采样使一段 1.5 s 的轨迹约 1500 个点。
- 实际运动比参考晚约 0.1 s，“到位”判定与阶段时长要计入。
- 加速度只用到 FCI 上限的 1/4，运动比真机能做到的慢（布局 14 的 7 个运动段合计约 6.0 s，全限值约 3.5 s）。
- joint5~7 的力矩上限只有 12 N·m，光滑参考下是否饱和未测。
- executor 新增对 `moveit_core` 的依赖。

## 被否决的做法

- **速度积分（resolved-rate / CLIK、每步一次带约束的 QP）生成参考：** 不规划轨迹、按剩余误差定速度时，起步速度跳变、收敛有长尾，加加速度约束后又不知何时刹车；离线或在线跑都一样，问题在于每步只看眼前。CLIK 的标准用法是跟踪一条已规划好的轨迹，那就已经是本决策的前半部分。
- **在线速度级控制（每个周期用实测值解 QP）：** 能对扰动反应，但等于把 executor 从“每阶段一个目标”改成“每周期一个速度”，改动很大，当前不需要。
- **所有段都走 TCP 直线：** 要逐点 IK、要处理解的跳变；搬运、回 HOME 离物体远，不需要。
- **加速度取 FCI 全值、之后用 Ruckig 补加加速度：** 快约 40%，但多一个环节，且在补上之前真机不能执行；用户选择 1/4（Week 5 Stage 3 的 3.3）。
- **自己写梯形速度：** 对两点直线足够（每段三个数），少一个依赖；但以后要曲线路径时还得换成 TOTG，用户选择一开始就用 TOTG。
